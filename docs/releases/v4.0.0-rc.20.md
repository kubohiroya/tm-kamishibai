## 対象

- 埋め込むTeachable Machine拡張を3.5.0にする（カメラプレビューをネイティブ解像度で描き、推論を
  テンソル経路へ移す）

## 概要

3.4.1までのポーズ認識は、カメラ映像を読み取り用の2D canvasへ描き写し、その小さな画像をプレビューにも
推論にも使っていました。canvasの大きさはモデルの入力寸法に合わせてあるので、プレビューはモデルの
解像度まで落ちたものでした。

3.5.0は二つを切り離します。プレビューは`<video>`をそのまま映すのでカメラのネイティブ解像度で、推論は
`tf.browser.fromPixels`でGPU上のテンソルを作り、中央を正方形に切り出して左右反転したものを使います。
読み取り用canvasを経由しないので、プレビューの見え方と推論の入力はもう互いの都合に縛られません。
骨格のoverlayは、切り出した座標を元のフレームへ戻してから描きます。

認識の精度そのものは変わりません。入力がネイティブ解像度になることで、モデルへ渡る前の縮小が一度に
なります。

## 互換性

- DSL document versionは引き続き文字列`kamishibai: "4.0"`です。
- Extension IDもbundleのmemberも変わりません。rc.19のStandard SB3で作った作品はそのまま開けます。
- block surfaceとcomposition APIは変わりません。台本に書くことは何も増えません。
- `poseRecognition.preview`の宣言（位置・不透明度・controls・mirroring）の意味は変わりません。

### 下流への影響

Standard SB3のバイト列が変わるため、公開済みartifactをベースとして固定している下流は再pinが必要です。

## 検証

```sh
pnpm verify:full
pnpm pack:smoke
pnpm release:check
```

ブラウザでの確認は、カメラのあるChromiumでpackagedチュートリアルを再生して行いました。この過程で、
samplesのpackaged-web検証がこのpinで落ちることが分かりましたが、原因は拡張ではなく検証側が
フェイクカメラの映像に依存していたことでした。チュートリアルの`Student.pose`は確信度0.5を1秒保てば
成立し（`idleChargePerSecond`は0）、Chromiumの既定のフェイクカメラ（色の帯が流れていく動画）を3.5.0の
切り出しで読むと`頭を守る`が56〜85%（従来の切り出しでは1〜3%）になるため、ポーズ待ちが読み飛ばし操作
より先に自力で成立していました。検証側を一色の静止画に直したうえで
（kubohiroya/turbowarp-kamishibai-samples#158）、このpinを入れたapp候補で通過することを確認しています。

## ロールバック

rc.20を同じversionで差し替えません。問題時は公開済みrc.19または安定版3.2.3を利用します。Teachable
Machine拡張だけを戻したい場合は3.4.1をpinしたcandidateを切れば、読み取り用canvasを経由する従来の
経路へ戻ります。
