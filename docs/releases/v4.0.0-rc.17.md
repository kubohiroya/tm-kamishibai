## 対象

- 埋め込みTeachable Machine拡張を`@kubohiroya/turbowarp-teachable-machine@3.4.1`へ
- rc.16でポーズ認識のカメラが起動しなかった不具合の修正

## 概要

rc.16はCamera Sourceを同梱し、Teachable Machine拡張がそこからleaseを取る構成にしました。その経路が
壊れていました。Teachable Machine 3.4.0は`Webcam canvas does not provide a 2D context`で落ち、
**Camera Sourceが居る環境ではカメラがまったく起動しません**。rc.16はCamera Sourceを常に同梱するので、
rc.16で作った作品のポーズ場面は進みません。

原因は上流のcamera helperの形です。readback canvasを、デバイスを開く分岐の**内側**で作ります。

```js
async setup(options) {
  if (!this.webcam) {
    this.webcam = await this.getWebcam(options)
    if (!this.canvas) { this.canvas = document.createElement('canvas') ... }
  }
}
```

leaseでは映像要素を注入するのでこの分岐ごと飛び、`getUserMedia`だけでなくcanvasも作られません。
3.4.0はこの2つが別だと見なしていました。3.4.1は、分岐が作ったはずのcanvasを拡張側で作ります
（[turbowarp-teachable-machine#93](https://github.com/kubohiroya/turbowarp-teachable-machine/pull/93)）。
下流が前提にしている320×240のミラー済み中央cropは変わりません。

見つけたのはturbowarp-kamishibai-samplesのpackaged-web browser checkです。rc.16を取り込んで
チュートリアル作品を再生したところ、ポーズ場面がskip入力を受け付けず、ページのerrorに上記が出ていました。
app側のtestはカメラを持つブラウザで作品を最後まで動かさないため、ここまで素通りしました。

## 互換性

- DSL document versionは引き続き文字列`kamishibai: "4.0"`です。
- Extension IDもbundleのmemberも変わりません。rc.16のStandard SB3で作った作品はそのまま開けます。
- block surfaceとcomposition APIは変わりません。変わるのは同梱するTeachable Machine拡張のバイト列と
  version文字列だけです。
- rc.16はポーズ認識を使う作品には使えません。カメラを使わない作品には影響しません。
- 3.1／3.2作品は推奨安定版3.2.3で継続利用できます。

### 下流への影響

Standard SB3のバイト列が変わるため、公開済みartifactをベースとして固定している下流は再pinが必要です。
turbowarp-kamishibai-samplesは`stories/urashima/dsl4-build.config.json`の`runtime`で固定しています。
rc.16はpinせず、rc.15から直接rc.17へ移ります。

## ロールバック

rc.17を同じversionで差し替えません。問題時は公開済みrc.15または安定版3.2.3を利用します（rc.16は
上記のためポーズ認識には使えません）。修正は次のcandidateとして公開します。npm dist-tag、
download catalog、Pagesの推奨表示だけを直前の検証済み組へ戻し、公開済みSB3、release metadata、
旧URL、旧packageの履歴は削除しません。
