# 4.0.0-rc.81 — 保存形式の指定とremoteアセットの検証済み保持コピー

関連: [App #1109](https://github.com/kubohiroya/turbowarp-kamishibai-app/pull/1109)、[App #1110](https://github.com/kubohiroya/turbowarp-kamishibai-app/issues/1110)。DSLは`4.0`、Camera Sourceは`0.22.1`を維持する。公開済みrc.80以前のmetadata・tag・配布物は変更しない。

## 変更範囲

「形式を指定して保存」の土台を入れる。SB3が持つ機能拡張・ソースデータ・アセットについて、`remote`／`cached`／`embedded-file`／`embedded-data`のどれで保持するかを名前で選べるようにし、まず機能拡張を書き換えるCLIを提供する。Plus形式（`project.json.turboWarpPlus`のManifest）は`@kubohiroya/turbowarp-extension-loader` 0.2.0で検証し、loaderの外部仕様から外れないようにする。`cached`形式はloader 0.2.0で追加・公開したものである。

`save-sb3-format`は4形式×3種類の共通語彙を持ち、書けない組み合わせは理由付きで拒否する。黙って格下げせず、黙って無視しない。指定しなかった種類はそのまま残す。本コマンドが書き換えるのは機能拡張だけで、ソースデータとアセットは指定すると拒否し、指定しなければ保持する。機能拡張の読み書きは1つのwriterに集約し、自身の出力に再実行しても変化しない。

既存Manifestの`execution`・`dependencies`・`capabilities`・`publisher`・`version`を保つ。sandboxedをunsandboxedへ昇格させない。data: URL由来の拡張はApp自身のDSL 4.0拡張3件だけを既定でunsandboxedとし、他は`--unsandboxed-extensions`で明示する。`--keep-embedded-data`を付けるとPlus形式の横にdata: URLを残せるため、標準TurboWarpでも読める。PlusホストではLoaderがManifestのIDを`extensionURLs`から外すので二重には読まない。

remoteアセットについては`delivery: remote`を変えず、bundleが予約パス`retained-remote`にバイト列を持てるようにする。remoteを二値で分岐している既存の経路は影響を受けない。保持コピーは任意で、payload自身のSRIに加え、remote sourceがhexで固定したバイト列そのものかも照合する。`materialize`はネットワークより先に保持コピーを使い、`recognitionModel`は取得時と同じくpose archiveとして展開する。binary-entry形式はfileアセットしか格納しないため、保持コピーを黙って落とさず`K4-ASSET-ENTRY-RETAINED-001`で拒否する。

[rc.80](v4.0.0-rc.80.md)の共通データソース契約、[rc.79](v4.0.0-rc.79.md)のタイトルカメラ判定、[rc.78](v4.0.0-rc.78.md)の依存初期化と作品読込後の再接続、[rc.77](v4.0.0-rc.77.md)の既定OFFプレビューとAsset Cache隔離patchを維持する。

## 制約

保持コピーを作るビルドコマンドはまだない。bundleとruntimeは扱えるが、`build-dsl4`等が予約パスを供給する経路は未実装で、現時点ではテストからしか到達しない。CLIの拒否理由にもそう明記している。

`build-dsl4`の出力は変わらない。ビルドは自動でPlus形式へ変換せず、data: URLのまま出力する。Plus形式にしたいときは`save-sb3-format`を明示的に使う。

## 検証・公開・切戻し

4形式×3種類の受理・拒否、writerの再実行での不変性、Manifestの保持項目、sandboxed昇格の不在、embedded-file ⇄ embedded-dataの往復でdata: URLがバイト単位で元へ戻ること、保持コピーのSRIとremote source hexの二重照合、binary-entry形式での拒否を対象テストで確認する。公開済み`kamishibai-4.0.0-rc.46.sb3`を使った往復と、実ファイルに対する`save-sb3-format`の実行も確認する。実ブラウザでの再生確認（Plusホスト・標準TurboWarpとも）は本候補の凍結後に行う。

公式driverによるrc.81の生成・凍結と公開後のhash照合を分け、候補の存在だけで公開完了を主張しない。rc.80から引き継ぐ課題として、npm公開前に`@kubohiroya/turbowarp-document-source`のgit pin参照の扱いを決める必要がある。

切戻しは`save-sb3-format`を使わなければよく、ビルドの既定出力はrc.80と同一である。配布物を戻す場合は公開済みのrc.80 SB3へ戻す。既存版を上書きせず、修正が必要なら次のrcを作成する。
