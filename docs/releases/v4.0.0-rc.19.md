## 対象

- ポーズ認識を使う作品のタイトルに、カメラの許可段（`<usermedia>`）を出す

## 概要

Chrome 151のCapability Element `<usermedia>`は、カメラの受け渡しを丸ごと持ちます。ページは要素の中に
ボタンを置くだけで、promptはブラウザが描き、`MediaStream`は要素が返します。これで**誰が訊けるか**が
変わりました。`MediaStream`はtransferableでもserializableでもないので、ギャラリーのページが取ったものを
遷移の向こうへ渡すことはできません。作品を再生するドキュメントが訊くしかなく、packaged作品はまさに
そのドキュメントです。

訊く場所はタイトルです。人はもともとそこをタップしますし、`<usermedia>`はpromptを開くのに自前のタップを
要します。描くのは3条件が揃ったときだけで、どれか欠ければ何も描かず、カメラは従来どおり読む側が
開きます。

- 作品がポーズを認識する
- ブラウザが`<usermedia>`を持つ（Chrome 151以降）
- `dsl4UserMediaPermissionGate`がON（Standard productionでON）

「作品がポーズを認識するか」は、artifactが運んでいる台本から読みます。runtime hostが台本を解析するのは
作品が始まるときで、そのときタイトルはもう終わっています。`runtime.extensionStorage`には同じ台本が
数KBのオブジェクトとして載っています。`vm.toJSON()`でも届きますが、そのためにプロジェクト全体を直列化
します——20MBのチュートリアルで書き出し28ms、parse 16ms、タイトルが出るべきフレームで払う費用です。

許可されたstreamはCamera Sourceの`pose` cameraIdへ渡します。これはTeachable Machine拡張がleaseする
idなので、認識はすでに開いているカメラを見つけ、`getUserMedia`を呼びません。Camera Sourceは預かった
streamのtrackを止めないので、作品が止まるときに入口が止めます。**ページが取ったカメラは、ページが
止めます。**

許可しないことは失敗ではありません。ボタンは残って再試行を誘い、作品はどちらでも始まります。認識は
必要になった時点で自分のカメラを開きます。

## 互換性

- DSL document versionは引き続き文字列`kamishibai: "4.0"`です。
- Extension IDもbundleのmemberも変わりません。rc.18のStandard SB3で作った作品はそのまま開けます。
- block surfaceとcomposition APIは変わりません。台本に書くことは何も増えません。
- `<usermedia>`を持たないブラウザ、ポーズを使わない作品では、見た目も挙動も変わりません。
- 3.1／3.2作品は推奨安定版3.2.3で継続利用できます。

### 下流への影響

Standard SB3のバイト列が変わるため、公開済みartifactをベースとして固定している下流は再pinが必要です。

## 検証

```sh
pnpm verify:full
pnpm pack:smoke
pnpm release:check
```

ブラウザでの確認は、Playwrightが積むChromiumが149で`<usermedia>`はChrome 151からのため、**要素だけ**を
差し替えて行いました。その先はapp shell、Camera Source、Teachable Machine拡張、canvasの
`captureStream()`による本物の`MediaStream`です。packagedチュートリアルで、タイトルに段が出ること、
許可後にCamera Sourceの`pose`が640×480で動くこと、ポーズ場面がskipを受理すること、そして
**`getUserMedia`が最後まで一度も呼ばれないこと**を確認しています。

## ロールバック

rc.19を同じversionで差し替えません。問題時は公開済みrc.18または安定版3.2.3を利用します。許可段だけを
止めたい場合は`dsl4UserMediaPermissionGate`をOFFにしたcandidateを切れば、従来のカメラ取得へ戻ります。
